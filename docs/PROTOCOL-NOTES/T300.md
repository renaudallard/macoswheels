# Thrustmaster T300 family protocol

Derived from [Kimplul/hid-tmff2](https://github.com/Kimplul/hid-tmff2)'s
`src/tmt300rs/`. This family — T300 RS, TX, TS-XW, TS-PC Racer, T248, T-GT —
shares one wire protocol distinct from the older T150's.

## USB identities

Same boot/firmware story as the T150. Shared boot PID `044F:B65D` plus a
per-model firmware PID.

| Wheel         | Firmware PID | Boot switch value |
|---------------|--------------|-------------------|
| T300 RS PS3 normal | `B66E`  | `0x0005` |
| T300 RS PS3 adv    | `B66F`  | `0x0005` |
| T300 RS PS4 normal | `B66D`  | `0x0005` |
| TX                 | `B669`  | (not in `hid-tminit` table) |
| TS-XW              | `B692`  | (not in `hid-tminit` table) |
| TS-PC Racer        | `B689`  | (not in `hid-tminit` table) |
| T248               | `B696`  | (not in `hid-tminit` table) |
| T-GT               | `B68E`  | (not in `hid-tminit` table) |

Wheels not in `hid-tminit`'s explicit table likely just need their attachment
discovered at runtime via the same `0xC1, 73` model query; switch values for
TX/TS-XW/TS-PC/T248/T-GT need confirmation against actual hardware before the
DEXT boot personality can flip them.

## Settings packets

Different command space from the T150. From
`hid-tmff2/src/tmt300rs/hid-tmt300rs.c`:

| Setting       | Bytes                                        |
|---------------|----------------------------------------------|
| Gain          | `[0x02, gain >> 8]` (high byte of 16-bit gain) |
| Range         | `[0x08, 0x11, scaled_lo, scaled_hi]` where `scaled = degrees * 0x3C` |
| Autocenter    | `[0x08, 0x04, value_lo, value_hi]` where `value = percent * 100` |
| Autocenter en | `[0x08, 0x04, 0/1, 0]`                       |

`Sources/Drivers/Thrustmaster/TMCommon/T300Settings.swift` is the Swift mirror.

Range clamp: `[40, 1080]` degrees. Below 40 is clamped; above 1080 is clamped.

## FFB upload — single packet per effect

Different from T150's three-packet sequence: the T300 family uploads each
effect as one larger packet on interrupt-OUT 0x02 with a fixed header and an
effect-specific body.

```
header: [0x00, slot+1, opcode]
```

`slot` is 0-based on the PID side; the wheel addresses slots as 1-based, hence
`slot + 1`. Opcodes:

| Opcode | Effect type   |
|--------|---------------|
| `0x6A` | Constant      |
| `0x6B` | Periodic / Ramp |
| `0x64` | Condition (spring/damper/friction/inertia) |
| `0x89` | Play / stop control |

### Constant (opcode 0x6A)

```
header (3 bytes)
+ level             (int16 LE, halved per Windows driver: stored / 2)
+ envelope          (8 bytes: attack_length, attack_level, fade_length, fade_level — all uint16 LE)
+ zero              (1 byte)
+ timing            (10 bytes; see below)
```

The level halving is `hid-tmff2`'s `t300rs_calculate_constant_level`:
"the Windows driver uses the range [-16385; 16381]".

### Condition (opcode 0x64) — spring/damper/friction/inertia

```
header (3 bytes)
+ right_coeff       (int16 LE)
+ left_coeff        (int16 LE)
+ right_deadband    (int16 LE, clamped to [-0x7FFF, 0x7FFF])
+ left_deadband     (int16 LE)
+ right_saturation  (uint16 LE; max 0x6AA6 for spring, 0x7FFC otherwise)
+ left_saturation   (uint16 LE)
+ 8 hardcoded bytes: 0xFE 0xFF 0xFE 0xFF 0xFE 0xFF 0xFE 0xFF
+ max_right_sat     (uint16 LE)
+ max_left_sat      (uint16 LE)
+ type              (1 byte: 0x06 spring, 0x07 damper / friction / inertia)
+ timing            (10 bytes)
```

Deadband math: `right = center + deadband/2`, `left = center - deadband/2`,
clamped.

### Periodic (opcode 0x6B)

```
header
+ magnitude (int16 LE)
+ offset (int16 LE)
+ phase (uint16 LE)
+ period (uint16 LE)
+ marker = 0x8000 (uint16 LE)
+ envelope (8 bytes)
+ waveform (1 byte: 0x01 square, 0x02 triangle, 0x03 sine,
                    0x04 sawUp, 0x05 sawDown) - derived as Linux FF_* - 0x57
+ timing (10 bytes)
```

### Ramp (opcode 0x6B, different body)

```
header
+ slope = abs(start - end) / 2  (uint16 LE)
+ center = (start + end) / 2    (int16 LE)
+ 2 bytes zero
+ duration (uint16 LE)
+ marker = 0x8000
+ envelope (8 bytes)
+ invert byte: 0x04 (rising) or 0x05 (falling)
+ timing (10 bytes)
```

### Play / stop (opcode 0x89)

```
play: [0x00, slot+1, 0x89, 0x41, count_lo, count_hi]   # 6 bytes total
stop: [0x00, slot+1, 0x89, 0x00]                       # 4 bytes total
```

### Timing block (10 bytes)

```
[ 0x4F,                  // start marker
  duration_lo, duration_hi,
  0x00, 0x00,            // zero1[2]
  offset_lo, offset_hi,
  0x00,                  // zero2
  0xFF, 0xFF ]           // end marker
```

Duration `0xFFFF` means infinite (Linux's `length = 0` translates to this).

## Effect coverage

All five PID periodics, constant, ramp, and the four condition kinds
(spring/damper/friction/inertia) are encoded for every T300-family driver.
`Sources/Drivers/Thrustmaster/TMCommon/T300FFBEncoder.swift`.

T128 has its own protocol that's neither T150 nor T300 — its driver currently
throws `notImplemented` until a `usbmon` capture is available.

## hid-tmff2 references

- `t300rs_upload_constant` — opcode 0x6A
- `t300rs_upload_periodic` — opcode 0x6B + waveform byte
- `t300rs_upload_ramp` — opcode 0x6B with slope/center/invert layout
- `t300rs_upload_condition` — opcode 0x64
- `t300rs_calculate_constant_level` — halving
- `t300rs_condition_max_saturation` — 0x6AA6 spring vs 0x7FFC others
- `t300rs_condition_effect_type` — 0x06 spring vs 0x07 others
- `condition_values[]` — the 8 hardcoded `0xFE 0xFF...` bytes
