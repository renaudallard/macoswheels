# Thrustmaster T150 protocol

Derived from [scarburato/t150_driver](https://github.com/scarburato/t150_driver)
and [scarburato/hid-tminit](https://github.com/scarburato/hid-tminit). The T150
is also the smallest wheel in the T-series and a useful reference: its protocol
is older and simpler than T300's.

## USB identity

| State            | VID    | PID    |
|------------------|--------|--------|
| Boot (generic)   | `044F` | `B65D` |
| Firmware (T150)  | `044F` | `B677` |

All T-series wheels enumerate first at the shared boot PID `B65D` as
"Thrustmaster FFB Wheel". They reveal themselves and accept FFB only after a
vendor control transfer flips them into a model-specific firmware PID.

## Boot to firmware switch (`hid-tminit` flow)

1. **Query model.** Control request:
   - `bmRequestType = 0xC1` (vendor, IN, device)
   - `bRequest = 73` (`0x49`)
   - `wValue = 0`, `wIndex = 0`, `wLength = 16`
   - Response bytes 6 and 7 carry `attachment` and `model` (in `tm_wheel_response.b`).
2. **Look up the switch value.** For the T150: `model = 0x03`, `attachment = 0x06`, `switch_value = 0x0006`.
3. **Send mode switch.** Control request:
   - `bmRequestType = 0x41` (vendor, OUT, device)
   - `bRequest = 83` (`0x53`)
   - `wValue = switch_value`, `wIndex = 0`, no data stage.
4. The wheel detaches and re-enumerates at `044F:B677`. The full HID interface,
   FFB endpoints and settings opcodes are now available.

The shared boot personality in `Sources/DEXT/Info.plist` matches `B65D`, runs
this two-control-transfer dance, and returns. The real driver personality
matches the per-model firmware PID and does the lifecycle proper.

Swift mirror of the model table lives in
`TMOpcode.modelQueryRequestType` / `modelQueryRequest` /
`modeSwitchRequestType` / `modeSwitchRequest` and `TMModelTable.entries`.

## USB endpoints (firmware mode)

T150 exposes two USB endpoints:

| Direction       | Address | Type      |
|-----------------|---------|-----------|
| Interrupt-IN    | `0x81`  | host reads input reports |
| Interrupt-OUT   | `0x02`  | host writes settings, FFB, control |

Both addresses live in `TMOpcode.interruptInEndpoint` and
`interruptOutEndpoint`.

## Settings packets (interrupt-OUT, opcode 0x40)

`Sources/Drivers/Thrustmaster/TMCommon/TMSettings.swift`.

All settings except gain share a single 4-byte format:

```
[0x40, op, arg_low, arg_high]    // little-endian uint16 argument
```

| op   | Meaning                       | Argument                              |
|------|-------------------------------|---------------------------------------|
| 0x03 | Set autocenter spring force   | `magnitude * 100 / 0xFFFF` (0..100)   |
| 0x04 | Enable / disable autocenter   | 0 = off, 1 = on                       |
| 0x11 | Set rotation range            | `degrees * 0xFFFF / 1080` (0..0xFFFF) |

Gain is a 2-byte packet with a different opcode:

```
[0x43, gain_low]                 // gain is uint16, only low byte is sent
```

## FFB upload (three-packet sequence)

The Windows driver — and `t150_driver.ko` — upload each effect as three
interrupt-OUT packets:

1. **`ff_first`** (11 bytes): envelope and slot keys, opcode `0xF0`. Carries
   attack length/level, fade length/level, and two slot-derived markers
   (`pk_id0 = slot * 0x1C + 0x1C`, used to correlate this packet with the
   later commit).
2. **`ff_update`** (4–8 bytes): the effect-class-specific parameters.
   - `0x03` (constant): one `int8 level` byte.
   - `0x04` (periodic): `magnitude, offset, phase, period` (Int8, Int8, UInt8,
     UInt16 LE).
   - `0x05` (condition): six small parameter bytes (right/left coeff, center,
     deadband, right_sat, left_sat).
3. **`ff_commit`** (15 bytes): correlates the previous two via `pk_id0`,
   declares the effect type code (`0x4000` constant, `0x4022` sine, `0x4023`
   sawUp, `0x4024` sawDown, `0x4040` spring, `0x4041` damper), duration, and
   start delay.

After commit, an effect-control packet starts/stops the effect:

```
[0x60, slot, control, repeats]
// control: 0x00 stop, 0x01 play, 0x41 play-and-loop
```

Mirrored in `Sources/Drivers/Thrustmaster/TMCommon/TMFFBEncoder.swift`.

## Effect coverage

| PID effect       | T150 native | Encoded |
|------------------|-------------|---------|
| Constant         | yes         | yes     |
| Square periodic  | yes         | yes     |
| Sine periodic    | yes         | yes     |
| Triangle periodic| yes         | yes     |
| SawUp periodic   | yes         | yes     |
| SawDown periodic | yes         | yes     |
| Spring           | yes         | yes     |
| Damper           | yes         | yes     |
| Friction         | no          | throws `effectNotSupported(.friction)` |
| Inertia          | no          | throws `effectNotSupported(.inertia)`  |
| Ramp             | not in protocol | throws `notImplemented` (could be synthesized as time-sliced constant) |
| CustomForceData  | no          | throws `effectNotSupported(.customForceData)` |

## Reference checklist before changing the encoder

1. The original assignment `buffer[1] = gain` in `t150_set_gain` is a
   `uint8 = uint16` narrowing in C; the high byte is silently dropped. Our
   Swift port mirrors this — `setGainPacket(percent:)` scales to a single byte
   `pct * 255 / 100`.
2. The autocenter `argument` is scaled into `[0, 100]` (a hardware percent),
   not the raw 0..0xFFFF magnitude PID would send. Don't pass through the raw
   PID value.
3. The rotation `argument` is scaled so 1080° == 0xFFFF. The wheel hardware
   accepts 270..1080°; values below 270 will be capped by the firmware.
